# 7. SLOs: Sloth specs, committed PrometheusRules, promtool tests, Slack alerts

Date: 2026-11-02
Status: Accepted

## Context

Metrics, traces and logs (ADRs 0004–0006) show what happened. They don't say
whether checkout is reliable enough, or when someone should be woken up. Stage
3's canary analysis also needs a burn-rate signal to abort on. The targets were
fixed when the roadmap was planned: checkout 99.9% available and 99% of
requests under 300ms, over 30 days.

## Decision

- **Two SLOs in `slos/checkout.yaml`** (Sloth's `PrometheusServiceLevel`
  format), both on `route="POST /checkout"` in namespace `shop`:
  - Availability 99.9%: errors are `code=~"5.."` over all requests.
  - Latency 99%: errors are all requests minus those in the `le="0.3"`
    histogram bucket.
- **Sloth runs as a CLI and its output is committed.** `make slo` writes the
  PrometheusRule to `gitops/monitoring/slo-rules.yaml`, which the existing
  `monitoring` Argo app deploys. The repo shows exactly what Prometheus
  evaluates, and no Sloth controller runs in the cluster. Tools are pinned in
  `mise.toml`: Sloth 0.16.0, promtool 3.15.1 (the cluster's Prometheus) and yq
  4.54.1.
- **Unit tests with `promtool test rules`** (`make slo-test`). `yq` extracts the
  rule groups from the PrometheusRule, because promtool can't read the CRD. The
  tests check that:
  - a sustained 5% error rate fires both the page and the ticket alert;
  - a 0.05% error rate fires nothing within 2h.
  A 0.5% error rate must fire only the ticket; asserting a page there makes the
  test fail, so the test catches broken thresholds.
- **CI workflow `slo.yaml`.** It runs `make slo`, fails on `git diff`, then runs
  `make slo-test`. `jdx/mise-action` installs only the three SLO tools.
  Actions are pinned to commit SHAs. `mise-action` is pinned to v5.2.0, a
  release over two weeks old, rather than the release published that day.
- **Alertmanager sends only SLO alerts to Slack.** The route's default receiver
  is `null`; alerts with `severity` `page` or `ticket` (only Sloth uses those)
  go to a Slack incoming webhook with `send_resolved`. The chart's own alerts
  (`warning`, `critical`, several always firing on kind) go nowhere, so no
  silences are needed.
- **The webhook URL is a SOPS secret** (`alertmanager-slack.sops.yaml`, built by
  KSOPS), mounted through `alertmanagerSpec.secrets` and read with
  `api_url_file`. It is never in the chart values or the rendered config.

## Rejected

- **The Sloth Kubernetes controller.** One more component to run, and the
  generated rules would no longer be reviewable in a PR.
- **Pyrra.** It has a UI, but it's another controller and its alerting is less
  configurable than Sloth's.
- **Custom alert windows (page 2%/1h, ticket 5%/6h).** Sloth requires a quick
  and a slow window per severity, so a single ticket window can't be
  expressed. Sloth's default 30d set is used instead:

  | Severity | Fires on |
  |---|---|
  | page | 2% of budget in 1h (5m short window), or 5% in 6h (30m) |
  | ticket | 10% in 1d (2h), or 10% in 3d (6h) |

  It still pages on 2% in 1h. The planned 5%-in-6h ticket now pages instead,
  which is what the Google SRE workbook recommends.
- **Discord.** Both work through a webhook; the owner already had a test Slack
  workspace.

## Consequences

- **Small objectives are rounded in float.** Sloth renders 99.9% as an error
  budget of `0.0009999999999999432`. Harmless, but it shows up in the rules.
- **The ticket alert outlives the incident.** After the burn test the page
  resolved after 14 minutes of clean traffic; the ticket stays active for
  hours because its windows are 2h and 1d. Expected for a ticket.
- **Idle services keep alerts firing.** With no traffic the 30m and 6h ratios
  keep the last errors, so the page only clears once healthy traffic dilutes
  them. A k6 baseline load (#11) avoids this in demos.
- **`sops decrypt` needs `SOPS_AGE_KEY_FILE` on macOS.** sops looks for the age
  key under `~/Library/Application Support/sops/age/`, but this repo keeps it
  at `~/.config/sops/age/keys.txt` (ADR 0002).
- **The latency SLO is not unit-tested.** Only availability has promtool tests.
- **Verified on the live cluster:**
  - Prometheus loaded 6 Sloth groups (34 rules), all healthy, with 4 alerts:
    availability and latency, each page and ticket.
  - With `ERROR_RATE=0.5` on checkout, 912 of 1800 requests failed over 7
    minutes. Both availability alerts fired about 2 minutes after the errors
    began.
  - Slack received `[FIRING] CheckoutAvailabilityBudgetBurn (page)` and
    `(ticket)` (confirmed in the channel). Alertmanager counted 3 Slack sends,
    the third being the page's `[RESOLVED]`, and 0 failures.
